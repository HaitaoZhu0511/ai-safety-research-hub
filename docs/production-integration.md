# 从离线控制到SLG、AI短剧与审核中台

本文是工程设计与试点路线，**没有在本仓库接入真实数据库、业务系统或人审队列**。不推断大厂未公开的内部架构。先阅读[已完成修复与边界](control-hardening.md)，再按以下验收门槛建设。

## 1. 共用底座，分开业务责任

共用：身份与权限、政策版本、预算、批准、执行回执、审计、评测和观测。分开：SLG指标语义、游戏名单处置、短剧内容审核、素材权利和发布门禁。不能用“同一个Agent”替代这些业务决策者。

| 层 | 负责人/接口 | Agent能做什么 | Agent不能自行做什么 |
| --- | --- | --- | --- |
| 数据语义 | 分析/数据平台，指标服务 | 解释口径、提出取数计划 | 创造新口径或越权读取明细 |
| 风险判断 | 策略/算法/审核运营 | 整理证据、提出候选结论 | 把模型分数当已确认违规 |
| 权利与资质 | 版权/法务/业务授权系统 | 检索有效证明及适用范围 | 将内容安全通过视为权利有效 |
| 批准与执行 | 独立审批服务、业务执行器 | 提出动作、查询批准状态 | 自批封号、外发、发布或扣款 |
| 评测与发布 | QA/策略负责人/工程 | 生成评测与差异报告 | 直接改生产阈值或绕过发布门禁 |

每次取数回答应交付：指标定义版本、授权范围、时间窗口、数据水位、来源引用、单位、查询回执和不确定性。缺权限返回受限结果；缺口径先澄清；无证据不编造SQL执行成功。

## 2. 幂等、恢复与累计预算

### 执行账本（待实施）

建议持久化key=(tenant_id,principal_id,request_id)，并保存提案、完整政策/授权快照的摘要、批准引用、状态、外部幂等键、回执与审计引用。对key建立唯一约束；同key不同摘要拒绝，成功请求只取回原回执。

建议状态：proposed → awaiting_approval → ready → executing → succeeded；另设rejected、expired、revoked、failed_no_effect、unknown_effect。审批记录与执行账本关联，但人审等待期间不能保持长数据库事务。

数据库事务用于原子领取与状态转移，可按竞争情况选择唯一约束、条件更新或行锁。PostgreSQL的FOR UPDATE阻塞竞争更新/锁定，锁通常持续到事务结束；不能把等待人审放进这个事务。[官方锁文档](https://www.postgresql.org/docs/current/explicit-locking.html)（核验：2026-09-30）。

上述数据库能力不使外部接口和本地账本天然构成一个事务。执行器应使用稳定的外部幂等键，并查询外部回执；超时或“外部成功、本地未落账”进入unknown_effect核对，不能无条件重试。下游不支持幂等/状态查询时，明确人工对账、可恢复补偿与剩余风险，不宣称exactly-once。

故障验收至少覆盖：两个工作进程竞争同key；领取后崩溃；外部成功后落账失败；响应丢失；批准撤销后领取；重启恢复；同key改参；审批到期。证据是外部实际动作次数和账本状态，不只是HTTP成功次数。

### 预算与隐私额度（待实施）

单次100行限制阻止不了多次小批量累计导出。建议按用户、租户、任务和滚动时间窗分别管理查询扫描量、执行时长、返回字节、导出记录数、工具调用与推理成本。

执行前原子预占，执行后按实际消费结算；无副作用失败才释放相关预占，未知状态先保留。确切回执重试不重复扣“导出动作额度”，但读取回执的带宽/访问频率可另计。多维额度预占必须协调，不能用户额度扣了、租户额度未扣又继续执行。

设计验收：拆成十次小导出仍触发累计额度；多进程不得超售额度；不同租户互不扣账；跨日/滚动边界正确；未知执行不会被当作零消耗。额度数值由实际基线确定，此处不提供假想的通用安全阈值。

## 3. SLG取数与游戏风控

### 指标服务优先于任意SQL

先落地固定指标及参数模板：DAU、付费留存、联盟活跃、资源产消、交易异常。指标注册表应写清自然日/游戏日、地区时区、开服日、账号/角色口径、合服映射、退款是否回溯、币种及汇率版本、数据延迟。

同一问法必须绑定同一指标版本；收入、净收入、流水不能互换。异常付费或资源数据先排查延迟、补发、退款、活动和合服，再进入风险解释。模型负责转述与解释，不自行定义“异常即作弊”。

### 数据库权限不是提示词

数据库执行身份需最小权限；列权限、脱敏视图、租户/区服范围与只读限制在服务侧及数据库执行。若使用PostgreSQL RLS，超级用户和BYPASSRLS角色会绕过；表所有者通常也绕过，可用FORCE ROW LEVEL SECURITY使所有者受约束。不要让Agent使用拥有这些绕过能力的账号。[官方RLS文档](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)（核验：2026-09-30）。

生产设计还需验证：连接池回收后租户上下文清理；缺上下文默认拒绝；授权上下文只能由可信网关注入，不能让任意SQL自行改租户；缓存键含租户/指标/权限及数据版本；管理员与服务角色分别测试。对于小群体聚合，加入最小群体规模和相邻查询差分测试，避免用聚合结果反推个人数据。

名单流程：行为证据 → 风险候选 → 正常大R/联盟协同行为对照 → 人审或专家复核 → 独立批准 → 可恢复限制/处罚 → 申诉。取数Agent与封禁执行器使用不同权限。验收不仅看命中率，也看恢复时长、正常高价值玩家误处置、申诉样本选择偏差和处置后的真实风险变化。

## 4. AI短剧/漫剧数据库与资产血缘

### 不只存成片和一个审核结果

建议实体：项目、剧集、剧本版本、分镜、图像、音轨/声音、人物/授权主体、生成任务、权利证明、内容检测、发布包、渠道回执、申诉。资产按版本不可变引用；派生关系用parent_asset_version → child_asset_version记录，避免一处素材变更后下游仍显示“已通过”。

权利记录至少有证明引用、许可范围、地区、渠道、有效期、用途限制、复核人和状态。生成任务记录输入资产版本、模型/配置版本和输出摘要；不得公开托管真实声音、个人身份或合同。权利缺失或争议进入复核，不由模型猜测补齐。

发布决定建议取交集：内容政策通过 ∩ 权利/人物授权有效 ∩ 适用标识与渠道要求满足 ∩ 发布者有权限。标识只是其中一层；本仓库不提供具体法域的法律合规结论，落地须由法务核对当地要求。

### 血缘变更如何触发复审

授权撤回、到期或素材替换 → 标记相关源资产版本 → 沿派生关系定位受影响成片/营销素材 → 创建复审单 → 冻结新发布 → 经批准执行渠道级下架/替换 → 记录每个渠道回执。

不能仅改数据库一列就认为外部平台已下架；部分渠道失败进入重试/人工处理。复审通过产生新版本与新发布批准，不把旧批准复制过去。授权范围由业务/法务核实，不把所有撤回统一解释为必须删除所有历史资产。

验收：替换音轨只让相关派生版本失效；权利变化触发受影响渠道的复核；重新剪辑不能继承旧发布批准；检测失败与证据缺失不自动通过；重试不会重复发布。取数接口提供授权范围内的血缘和状态，不能直接返回合同原文或未授权人物信息。

## 5. 机审、人审、专家与申诉

详细基础见[人机审核运营](human-review-operations.md)。下一步应把文字流程实现为可持久化工单，而非让Agent对话记忆承担状态。

工单主键绑定业务对象版本、政策版本与队列；事件记录机器建议、人工判断、批准和处置四个不同事实。低置信、多模态冲突、缺资质进入人审；高影响处罚和政策争议进入专家。对自动通过、自动拦截双向抽检，不能只检查模型认为“有风险”的样本。

领取工单用租约/条件更新，保存owner、lease_until、状态版本。审核员掉线后可重新分配；迟到提交使用版本比较拒绝，避免旧审核员覆盖新结论。模型建议留存供复核，但盲审抽检不预先展示建议，评估锚定偏差。

申诉生成关联新单，由与原审人独立的复核者判断；涉及规则解释的分歧由政策负责人裁决。改处置要有恢复/补偿回执，不以“结案”代替真正恢复。机审的高分、人审的快处理都不能绕过敏感动作批准。

超时策略按业务设计：可保持受限、升级或提示补证，不默认通过。验收包括重复领取、超时升级、迟到提交、素材改版、原审人试图复核自己、已执行后翻案，以及证据访问越权。这里尚未实现租约、队列、申诉和恢复服务。

## 6. 降本增效：把产能、现金与风险分账

沿用[成本收益](cost-and-value.md)的成本口径，新增跟踪字段：正确结案量、人审有效时长、抽检成本、复审次数、误处置恢复成本、已确认漏放损失、商业转化及审核员工时去向。

净变化按同一期间、同一业务口径计算：基线可比成本 − 新推理/特征/平台成本 − 新人审/抽检/申诉成本 − 一次性投入的摊销 − 错误处置及风险损失增量。GMV、流水、收入、利润不能混在一个收益数里。

人审从10%降到7%首先意味着释放产能，只有实际减少外包账单、加班或可避免招聘等可核验支出才记现金节约。保留人力转入专家、QA与增长业务的量；不能既记减员现金节约又记同批员工新增业务产出。

试点按业务/时段/风险等级分层比较两套都满足底线的方案，记录随机分组或可比对照、流量结构与置信区间。指标至少同时看严重漏放、正常误拦、风险曝光、正确结案成本、p95等待时长和有效申诉恢复；样本不足时报告不确定性，不强行宣称胜出。

## 7. 建设顺序与交付门槛

| 阶段 | 交付物 | 升级条件 |
| --- | --- | --- |
| P0：控制账本 | 认证、持久批准/回执、原子领取、预算与审计锚点 | 多进程与崩溃恢复测试；不确定副作用可核对 |
| P1：只读试点 | SLG固定指标或短剧资产状态检索，影子模式 | 口径对齐、权限隔离、无敏感明细外发 |
| P2：人机协作 | 队列、专家复核、申诉、抽检、恢复回执 | 独立复核与超时/掉线/翻案演练 |
| P3：批准后动作 | 单一可恢复处置或单渠道发布，小范围灰度 | 风险底线、外部幂等、回滚与值班完成验收 |
| P4：效果评估 | 分层评测、成本/质量看板、漂移与发布门禁 | 有业务基线与可追溯证据再扩大范围 |

P0不是要求先建一个巨大平台；应为首个最小试点建设相应控制。任何阶段都不直接从离线演示跨到自动封禁或全渠道发布。本次只修复演示并补充路线，以上项目能力均标为待实施。
